The [PR checks](https://github.com/anglee0323/agy-switch/pull/120) (three-platform package jobs, optimized CLI jobs and complete-set verification), the main Build/Release CLI runs at the frozen source, and the [formal release workflow](https://github.com/anglee0323/agy-switch/actions/runs/41330569446) all passed, including complete-set validation and publication.

The public Mac ZIP, extracted in an owned temporary directory, reports version 4.10.13,
ARM64, a deployment target of macOS 11.0 and passes `codesign --verify --deep --strict`
with an ad-hoc signature (no team identifier). Its bundled console printed the new
`--target agy` help text and returned the expected JSON and exit code 3 for an unknown
account against an empty synthetic data directory. The bundle's empty-entitlement and
resource-seal checks ran in the release workflow. Gatekeeper acceptance and notarization
were not tested. The public ZIP was not installed over the maintainer's App.

The `--target agy` switch itself was verified separately on a Mac with real saved
accounts and the Antigravity App running (see the [release notes](../release-notes/4.10.13.md)):
the App kept its PID and start time, a new `agy` run used the new account, and the
original account was restored. That run used a locally built binary from the same source
change, not the published ZIP.

Not performed for this release: Windows/Linux package installation on native hosts,
PTY/ConPTY terminal runs and viewport checks against the public assets, update discovery
from 4.10.12, a real `--target agy` switch on Windows or Linux, and fresh Homebrew
installation, upgrade, custom app directory and uninstall. Mac packages lack Developer
ID/notarization and Windows packages lack Authenticode; bundle and updater signatures do
not establish OS trust. Live Google login and physical Windows/Linux tray behavior remain
separate acceptance.

The generated Homebrew recipe pins the public ZIP hash above; its required recipe check
fetches that archive and regenerates the recipe before merge.
